# 群组房间观战、邀请、容量与实时同步实施计划

> **面向自动化执行者：** 必须使用 `superpowers:subagent-driven-development` 按任务逐项实施；每项由新的 GPT-6 Luna 子代理完成，并在继续前进行独立审查。所有提交保留在当前已确认的功能分支。

**目标：** 为群组房间增加不限量只读观战席、统一邀请与身份选择、扩展房间容量，并让新加入或重连的联机客户端直接显示当前状态；移除手动倍速与快进，保留战斗自动加速。另将 `/status` 改为图形化状态页，持久保留最近 100 场已完成对局的结算信息。

**架构：** 网关继续管理房间码和跨服务器路由，另行维护玩家与观战者，并把开局后的房间码关联到活动比赛。比赛实例通过只读观察连接广播当前公开状态快照和后续实时消息；网页先查询房间状态、选择身份，再进入对应界面。比赛快照使用当前阶段数据和经过时间初始化客户端，不回放先前阶段或画面。`/status` 在保持现有本机/Tailscale 访问控制的前提下提供中文图形页；旧 JSON 数据由同样受限的 `/status.json` 返回。比赛实例把精简后的最终公开结果写入 `DUEL_LOGS`，图形页展示最近 100 场。

**技术栈：** Node.js ESM、`ws`、现有 JSON WebSocket 协议、浏览器 ES modules、当前确定性战斗模拟器；不增加依赖。

**规格：** `docs/superpowers/specs/2026-10-23-room-spectators-invites-capacity-speed-design.md`

## 全局约束

- 礼物对决群组房间容量为 8/16/24；竞猜对决群组房间容量为 30/60/90；公共匹配仍为 8/30。
- 房间容量创建时选定并固定；只有玩家成员占容量，观战席没有房间级独立人数上限。
- NPC 补位使用现有 28 人 NPC 池，补到所选容量或池耗尽，不扩充 NPC 名单。
- 邀请链接仅使用 `room` 查询参数携带六位房间码；所有加入入口先选择参加或观战，不创建单独观战链接。
- 比赛开局后，原房间码只允许观战；服务端必须执行身份权限和容量判断。
- 新连接和重连直接初始化到服务端当前阶段与进度，不重播历史事件或画面，不使用倍速追赶。
- 保留现有战斗播放曲线：战斗时间前 15 秒为 1 倍，45 秒升至 2 倍，90 秒升至 3 倍，之后保持 3 倍。
- 完成对局的历史最多保留最近 100 场，跨服务进程重启读取；部署容器时须持久挂载 `DUEL_LOGS` 才能跨容器重建保存。
- `/status` 与 `/status.json` 共用现有 loopback/Tailscale Serve 访问限制；`/healthz` 保持原响应和用途。状态页用内置 HTML/CSS/SVG 呈现当前状态，不新增外部图形依赖或历史指标采集。
- 历史只保存最终公开结算字段，不保存令牌、连接标识、头像、战斗种子或封盘前私有选择，也不提供逐帧回放。
- 用户已要求恶劣网络与刷新场景测试；本次稳定性修复增加相应回归测试，并在本机进行浏览器复测。每个任务提交前做代码审阅并运行 `git diff --check`。

## 接口约定

- 房间创建：`{ t: 'room.create', mode, capacity }`。网关按房间模式只接受礼物对决 `8 | 16 | 24` 或竞猜对决 `30 | 60 | 90`。
- 房间状态查询：`{ t: 'room.lookup', code }`。网关返回 `room.info`，包含 `code`、`mode`、`max`、`started`、`full`；`room.start` 接受后立即将 `started` 设为 `true`，即使实例仍在创建中。外部节点继续返回现有 `elsewhere` 消息。查询不占座、不更改房间状态。
- 加入房间：`{ t: 'room.join', code, role: 'player' | 'spectator' }`。`role` 缺省时按 `player` 处理。玩家席已满或比赛已开始时，网关拒绝玩家加入；等待房间中的观战者加入 `spectators` 集合。比赛实例创建期间，观战者可进入待发名单，在实例就绪后收到匹配信息。
- 房间广播：`{ t: 'room', code, mode, max, host, members, spectators, npc }`。`members` 与 `spectators` 始终分开计数和授权。
- 开局结果：玩家收到 `{ t: 'matched', role: 'player', port, matchId, token, mode }`；观战者收到 `{ t: 'matched', role: 'spectator', port, matchId, code, mode }`。只有玩家消息含玩家令牌。
- 比赛创建：网关传入选定的 `capacity` 和现有 `npcFill`；公共匹配不传 `capacity`，实例继续使用模式默认容量。
- 观战 WebSocket：浏览器向网关请求 `/match?port=<port>&m=<matchId>&code=<roomCode>`。网关只有在活动房间码映射到同一个比赛和实例时，才转发为实例内部的 `/match?m=<matchId>&watch=1`。
- 首次连接与重连：`hello` 包含 `role`、`mode`、`players`、`phase`、`seq` 和 `current`。`current` 的稳定字段为 `phase`、`elapsedMs`；按阶段可选包含 `round: { r, roundId, lineups, traps, commit, betMs, secretMs }`、`secret`、`publicChoices`、`seed`、`salt`、`result: { r, w, players }`。下注阶段的 `publicChoices` 不含封盘区间内的选择；只有玩家本人可获得 `ownChoice`，观战者没有该字段。战斗阶段的 `elapsedMs` 是服务器自战斗开始以来的真实时间，客户端按既有自动加速曲线换算模拟位置。后续消息继续使用单调递增的 `seq`。
- 状态页：`GET /status` 返回图形 HTML；`GET /status.json` 保留现有网关、房间、实例与队列 JSON 字段，并增加按结束时间倒序排列的 `history`（最多 100 场）。两个入口使用相同访问校验；`GET /healthz` 不变。
- 历史条目：包含对局标识、模式、开始/结束时间、时长、轮数和最终参与者结算摘要；详细字段按当前模式的最终排名、得分和公开统计展示。不得持久化头像、席位令牌、连接 ID、种子或封盘前私有选择。

## 重点审查

- **房间开局与邀请码竞态：** 查询显示可参加后房间可能满员或开局；`room.join` 必须重新校验并返回明确错误。对应任务 1 和任务 3 的代码审阅。
- **跨服务器路由：** 等待房间和活动比赛的六位码均需路由到持有该码的节点；无效码不得产生比赛连接。对应任务 1 和任务 3 的代码审阅。
- **观战权限与开局人数：** 观战连接不能获得玩家令牌、发送玩家操作、占玩家席或改变等待玩家观赛完成的条件。对应任务 2 和任务 4 的代码审阅。
- **竞猜公平性：** 封盘前的他人选择、未开放的战斗种子和结果不能进入观战或重连快照。对应任务 2 和任务 4 的代码审阅。
- **最大房间容量：** 90 名玩家的创建请求体不能因头像数据超过实例现有 1 MiB 限额；保持 NPC 池仍为 28。对应任务 2 的代码审阅。
- **状态页访问边界：** 图形页与 JSON 接口必须使用完全相同的 loopback/Tailscale Serve 检查；公网反向代理继续屏蔽 `/status` 前缀，`/healthz` 内容不变。对应任务 6 的代码审阅。
- **历史数据最小化和保留：** 只归档成功完成的比赛公开结果，多个实例并发完成时归档不能互相覆盖；服务进程重启后可读，列表和存储最多保留最近 100 场。对应任务 6 的代码审阅。
